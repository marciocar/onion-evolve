Aula 5 — KG e Forja: o grafo dos seus projetos e os componentes do seu time

Espelho em texto de lesson-5-kg-forge.html, com a mesma substância. A versão para projetar é a HTML: abre offline, tem botão de copiar em cada comando e modo projetor. Rascunho de 2026-10-14. A nota para o revisor fica no fim deste arquivo.

Série: formação de equipe de um hub adotante, em 6 aulas. Esta é a 5ª. Antes dela: (1) o "Há vagas", o perfil dos agentes que vocês querem; (2) os documentos de negócio; (3) a adoção dos projetos e a maquinaria; (4) um projeto real com task manager. Depois dela: (6) comunicação e federação, o Company Brain.

Duração: 3 horas, com um intervalo de 10 minutos. Formato: mão na massa. Cada bloco tem um conceito curto, uma demonstração com o comando exato e um exercício no repositório de vocês, com um critério de "pronto" que se confere por comando.

Objetivo

No fim da aula, cada dupla sai com cinco coisas no repositório, todas conferíveis:

  1. Um grafo que o motor lê. Os grafos do hub passam no kg-radar sem aviso e o /meta:drive os aceita.
  2. Um projeto mapeado contra o código. As regras de domínio de um projeto real apontam para o arquivo e a linha que as executam, e não só para o documento que as descreve.
  3. Um documento de negócio ligado ao projeto. Um documento das aulas 2 a 4 que ainda não estava em grafo nenhum vira nós, com a confiança certa, ligados às regras que ele afeta.
  4. Uma ferramenta de terceiro dissecada e decidida. Um grafo de dissecação com veredito e o nó de decisão selado, antes de qualquer adoção.
  5. Um componente do time forjado. Uma skill com doutrina, medidor e bancada, nascida de uma dor que vocês mediram (ou do plano de absorção da dissecação), e que o censo da forja enxerga.

E uma ideia: o grafo é o estado do trabalho, não um desenho dele. A sessão lê o grafo antes de ler a prosa, o backlog é projeção do grafo, e uma decisão só existe quando está selada nele.

Antes da aula (instrutor): medir a turma

A aula usa os artefatos reais da equipe como matéria-prima. Meça no dia, porque o repositório anda. Rode na raiz do hub e, depois, na raiz do projeto adotado que a equipe trouxe na aula 4:

for g in $(git ls-files '*.kg.yaml' | grep -v '/fixtures/'); do
  echo "== $g"; bash .claude/validation/kg-radar.sh "$g" --integrity --schema
done

Anote na ficha da turma (fica com vocês, não entra neste material):

Bloco A — O grafo como fonte única, e a gramática (20 min)

Conceito. Um .kg.yaml é um grafo tipado: nós com node_type: (o que a coisa é) e arestas com edge_type: (como as coisas se relacionam). Há duas camadas. A audit registra conhecimento: claim, evidence, decision, question. A domain registra o negócio: entity, state, event, rule, invariant, policy. O radar (kg-radar.sh) é awk, não um parser de YAML: ele exige uma chave por linha e reprova contradição estrutural. A gramática inteira, curta, está em .claude/rules/kg-grammar.md, e carrega sozinha quando a sessão toca um .kg.yaml.

Os cinco erros clássicos (todos da gramática da casa):

ErroPor que dói
escrever type: no lugar de node_type:/edge_type:o radar não lê; um grep por type: REFUTES devolve zero e a guarda nasce verde e vazia
nó recebe REFUTES e continua confirmedcontradição estrutural: o radar sai 1. Reconcilie para refuted/superseded
objeção que sobrevive modelada como REFUTESobjeção que mata é REFUTES; objeção que limita é CONSTRAINS
data sem aspas (verified_at: 2026-10-14)leitor YAML tipado a lê como data, outro como texto; escreva "2026-10-14"
--- separando um cabeçalho do restoo arquivo vira dois documentos YAML; o radar avisa e o /meta:drive e o kg-realign recusam

Demo.

bash .claude/validation/kg-radar.sh docs/onion/graph/onion-adoption.kg.yaml --integrity --schema
bash .claude/validation/kg-drive-project.sh docs/onion/graph/<um-grafo-com-aviso>.kg.yaml

Mostre o aviso ⚠ multi-documento: 2 separadores --- no radar e, logo depois, o /meta:drive recusando o mesmo arquivo com YAML ilegivel … expected a single document. É o mesmo defeito visto por dois leitores: um avisa, o outro trava.

Exercício. Consertem todos os grafos do hub que o radar acusa de multi-documento. A cura que o próprio radar sugere: tirar as linhas ---. Os campos do cabeçalho viram chaves de topo; nenhum dado muda.

for g in $(git ls-files '*.kg.yaml' | grep -v '/fixtures/'); do
  grep -q '^---$' "$g" && echo "multi-documento: $g"
done
# para cada um: apague as linhas que são exatamente '---' (no editor, ou peça à sessão)

Pronto quando:

bash .claude/validation/kg-radar.sh <grafo> --integrity --schema   # exit 0 e sem '⚠ multi-documento'
bash .claude/validation/kg-drive-project.sh <grafo>                # imprime 'veredito:' em vez de ERRO
git diff --stat                                                    # só linhas '---' removidas

Erros comuns e saída.

  • Apagou um --- que estava dentro de um texto |. O grep '^---$' só casa a linha inteira; confira no git diff que só saíram linhas de separador.
  • O drive agora mostra "bloqueado". Não é erro: DEPENDS_ON é guarda. Leia a aresta: ela sai do nó que depende.

Bloco B — Mapear um projeto real contra o código (30 min)

Conceito. Um grafo de domínio feito a partir de um documento diz o que alguém escreveu que o sistema faz. Quando o código chega, cada rule, invariant e policy precisa ser conferido nele, e a âncora (trace:) troca do documento para o arquivo:linha que executa a regra. Até lá, a confiança fica abaixo de 1. Re-verificar contra o vivo é o trabalho do /meta:kg-freshness: ele pega a fila do radar e, para cada nó, mede e propõe um veredito (CONFIRMED, DRIFTED, REFUTED, UNVERIFIABLE). Quem sela é a pessoa.

Duas trilhas, conforme o que o projeto já tem:

  • Trilha 1, o projeto já tem grafo de domínio (feito a partir do documento da feature): re-ancorar.
  • Trilha 2, o projeto não tem grafo: criar o primeiro, com /meta:kg map <área>.

Demo (trilha 1). No projeto adotado:

bash .claude/validation/kg-view.sh docs/onion/graph/<dominio>.kg.yaml --markdown | head -30
grep -nE '^\s+trace:' docs/onion/graph/<dominio>.kg.yaml        # para onde as âncoras apontam
bash .claude/validation/kg-radar.sh docs/onion/graph/<dominio>.kg.yaml --domain

Mostre a composição (quantas rule, quantas question), as âncoras todas em docs/ e o radar-de-domínio apontando lacunas, como um estado absorvente (um estado em que se entra e de onde não se sai: é fim legítimo ou limbo?). Depois procure uma regra no código, ao vivo:

grep -rn '<termo da regra>' apps/ packages/ | head

Demo (trilha 2).

/meta:kg map <área do sistema>

O modo map faz inventário, fatias de domínio e grafo, e fecha com o radar.

Exercício. Cada dupla pega três nós rule/invariant/policy e, para cada um:

  1. acha o código que executa a regra (grep -rn; o número da linha sai do grep -n, nunca de contar na tela);
  2. troca o trace: para apps/<…>/<arquivo>:<linha>;
  3. atualiza verified_at: "<data de hoje>" e verified_against: com o que foi lido;
  4. se o código não faz o que o rótulo diz: muda o status para drifted e escreve o porquê; se não achou o código: deixa a regra como está e cria um nó question ligado a ela.

Se o grafo tem uma pergunta do tipo "onde fica o código?", respondam-na e reconciliem para done.

Pronto quando:

bash .claude/validation/kg-radar.sh docs/onion/graph/<dominio>.kg.yaml --integrity --schema   # exit 0
grep -cE 'trace: (apps|packages)/' docs/onion/graph/<dominio>.kg.yaml                         # >= 3
bash .claude/validation/kg-trace-resolve.sh .                                                 # toda âncora resolve

Erros comuns e saída.

  • Linha citada de cabeça. Ela erra por uma ou duas e a âncora aponta para outra coisa. Copie o arquivo:linha da saída do grep -n.
  • Subir a confidence para 1 só porque achou o arquivo. Achar o arquivo não é ler a regra. Suba só depois de conferir que o código faz o que o rótulo diz.
  • REFUTES num nó que segue confirmed. O radar sai 1. Mude o status junto com a aresta.

Bloco C — Mapear um documento de negócio e ligar ao projeto (25 min)

Conceito. Os documentos das aulas 2 a 4 (personas, estratégia, features, decisões de trabalho) são prosa. Prosa não tem confiança, não tem dono e não avisa quando caduca. Levá-los ao grafo dá a cada afirmação um tipo, uma confiança e uma ligação com o que ela afeta. Uma regra boa para a confiança: o que o cliente confirmou pode ser confirmed; decisão de trabalho da equipe ("inferimos isto") é decision open com confidence menor; palpite é ainda menor; o que depende de informação que só o cliente tem é question.

Demo. Achar o documento que nenhum grafo cita:

for d in $(git ls-files 'docs/business-context/*.md'); do
  n=$(grep -l "$(basename "$d")" $(git ls-files '*.kg.yaml' | grep -v '/fixtures/') | wc -l)
  [ "$n" -eq 0 ] && echo "sem grafo: $d"
done

Mostre um nó de decisão de trabalho bem escrito (com narrative: para o porquê, porque o label tem teto de 280 caracteres):

  - id: D_LOGIN_OIDC_ANY_IDP
    node_type: decision
    plane: DEV
    status: open
    impact: 4
    confidence: 0.6
    verified_at: "2026-10-14"
    verified_against: doc-de-decisoes-da-feature-secao-1-marca-INFERIDO
    trace: apps/<servico>/src/auth.ts
    label: "Decisão de trabalho: login por qualquer IdP OIDC; o serviço não guarda senha."
    narrative: "Marcada [INFERIDO] no documento: a equipe decidiu, o cliente não confirmou."

edges:
  - from: D_LOGIN_OIDC_ANY_IDP
    to: PO_ACCESS_BY_PROFILE
    edge_type: CONSTRAINS

Exercício. Duas trilhas, a dupla escolhe:

  • No projeto: mapear o documento de decisões ou hipóteses da feature (se existir) no grafo de domínio do projeto. Uma decisão por nó; confiança pela marca do documento; trace: para o código quando o documento diz onde está; arestas CONSTRAINS/SUPPORTS/DEPENDS_ON para as regras que ela afeta.
  • No hub: responder a pergunta do grafo de adoção ("qual é o domínio deste repositório?"). Criem docs/onion/graph/<tema>.kg.yaml a partir de um documento de negócio da aula 2 (estratégia ou personas são bons pontos de partida) e reconciliem a pergunta do grafo de adoção para done, com verified_against apontando o grafo novo.

Pronto quando:

bash .claude/validation/kg-radar.sh <grafo> --integrity --schema      # exit 0
grep -c '<nome-do-documento>' <grafo>                                 # >= 1: o documento está no grafo
bash .claude/validation/kg-backlog-project.sh --markdown | head -20  # as perguntas novas aparecem

Erros comuns e saída.

  • Tudo vira confirmed. Decisão de trabalho não confirmada pelo cliente não é fato. O backlog existe para mostrar o que espera confirmação: se tudo for confirmed, a fila mente.
  • Label-parágrafo. Passou de 280 caracteres, o porquê vai para narrative:.
  • Id com ponto ou hífen. Só [A-Za-z0-9_]; o radar reprova o resto.
  • Ligar ao grafo de outro repositório. external_edges: liga grafos do mesmo repositório. Ligar o hub ao projeto é assunto da aula 6.

Intervalo (10 min)

Bloco D — O grafo como runtime (20 min)

Pré-requisito deste bloco, do E e do F: o hub num pin ≥ 6e6deab1c443 (onion-v1.2.0), que já traz o /meta:decide e o /meta:forge abertos para o papel hub. Confira com cat .claude/.onion-version e ls .claude/commands/meta/decide.md .claude/validation/kg-decide-seal.sh.

Conceito. Um grafo que só se lê na hora de escrever é documentação. Aqui ele dirige o trabalho: o /warm-up e o /catch-up o leem para abrir a sessão; o /meta:backlog projeta os nós open numa fila única, ordenada por atenção (impacto × incerteza × status); o /meta:realign confere se o plano ainda está alinhado (aligned) com o vivo, em três camadas (passado, presente, futuro); o /meta:drive conduz o plano nó a nó, a partir da fila pronta. A decisão também mora no grafo, e quem a fecha é o /meta:decide: ele mede o que está em voo, tira o que a sessão pode medir sozinha, pergunta o resto com opções e sela cada resposta no nó. Ninguém edita o selo à mão.

Demo 1: a fila e o plano.

bash .claude/validation/kg-backlog-project.sh --markdown | head -40     # a fila inteira, sem escrever arquivo
bash .claude/validation/kg-realign-project.sh docs/onion/graph/<grafo>.kg.yaml
bash .claude/validation/kg-drive-project.sh docs/onion/graph/<grafo>.kg.yaml
bash .claude/validation/kg-console.sh docs/onion/graph/<grafo>.kg.yaml > kg-console.html   # abra no navegador; não commite

No realign, mostre o commitment-drift: pergunta aberta de alto impacto sem nada que a apoie, com o radar perguntando "abandonado?". No drive, mostre a fila pronta e os bloqueados.

Demo 2: decidir com o /meta:decide. O comando tem quatro movimentos, e vale mostrá-los um a um:

  1. Medir. Na carga ele roda o censo do que está em voo (checkpoints, PRs e CI, worktrees, inbox, nós citados). Para ver o mesmo censo fora do comando:
bash .claude/validation/decide-census.sh . --markdown
printf '%s' "<texto que cita os ids>" | bash .claude/validation/decide-census.sh . --markdown --cite -

Os avisos (sem gh, teto atingido) vêm antes das linhas: ausência de linha com aviso não é zero.

  1. Filtrar. O que é medível, a sessão mede; o que deriva de decisão já selada, ela aplica; o que é de outro dono (outro repositório, merge, deploy), ela encaminha. Só sobra o que é de quem decide.
  2. Perguntar com opções. Até 4 perguntas por rodada, 2 a 4 opções cada, a recomendada primeiro com o porquê, e cada opção dizendo o custo e o que destrava. Faltou base: uma opção é "pesquisar antes".
  3. Selar. Cada resposta vira selo no nó antes da rodada seguinte, sempre pelo selador:
bash .claude/validation/kg-decide-seal.sh <grafo> <NODE_ID> \
  --chosen "<opção escolhida>" --rejected "<a|b>" --date <AAAA-MM-DD> --question "<a pergunta>"

Ele grava status: done, plane: DEV, a proveniência de testemunho e, na narrative, a opção escolhida e as descartadas. Sai 0 só com o radar --integrity --schema em 0; 2 quando recusou sem escrever nada (nó inexistente, já done, campo cego); 3 quando o radar reprovou e a escrita foi desfeita.

Exercício.

  1. Rodem o /meta:backlog e escolham um item que vocês podem decidir hoje.
  2. Rodem /meta:decide citando esse item. Respondam a rodada de perguntas.
  3. Confiram no git diff o que o selador escreveu no nó (status, proveniência, opções na narrative).
  4. Rodem o realign e o drive no grafo que mudou.

Pronto quando:

git diff --stat                                                                   # só o grafo do item mudou
bash .claude/validation/kg-radar.sh <grafo> --integrity --schema                  # exit 0
bash .claude/validation/kg-backlog-project.sh --markdown | grep -c '<ID_DO_NO>'   # 0: saiu da fila
bash .claude/validation/kg-realign-project.sh <grafo> --check                     # exit 0

Erros comuns e saída.

  • Editar o nó à mão para "adiantar". O selo diz quem decidiu, quando, e o que foi descartado. Use o selador; se ele recusou (rc 2) ou desfez (rc 3), leia a mensagem e conserte a causa.
  • Responder pela pessoa que decide. O /meta:decide não decide por ninguém e não sela o que não foi perguntado. Se a decisão é de outra pessoa (do cliente, por exemplo), ela fica open e a rodada registra de quem depende.
  • O radar avisa decision-done-em-DEV. Depende do pin: o selo fica em DEV de propósito, porque é testemunho e não medição. Não passem o nó para PROD para calar o aviso: o motor acusa testemunho em PROD como MISPLANED.
  • Editar docs/backlog.md à mão. É projeção: feche o nó no grafo e regenere. Se vocês commitarem docs/backlog.md, a REGRA 62 (Projeção GERADA em sincronia com a fonte (docs/backlog.md)) passa a cobrar que ele bata com a fonte; regenerem com /meta:backlog.
  • O drive para em CHECKPOINT-PENDENTE. É de propósito: um lote anterior espera selo. O selo de checkpoint é do drive (kg-drive-project.sh <grafo> --seal), não do selador do decide.

Bloco E — Dissecar antes de adotar: o /meta:dissect (25 min)

Pré-requisito: o mesmo pin dos blocos D e F (≥ 6e6deab1c443 (onion-v1.2.0)), que traz o /meta:dissect aberto para o papel hub. Confira com ls .claude/commands/meta/dissect.md .claude/validation/dissect-census.sh .claude/validation/dissect-plans.sh.

Conceito. Antes de forjar, a pergunta é se alguém lá fora já resolveu a dor. O /meta:dissect mapeia uma ferramenta de terceiro numa escada de cinco níveis, e nível reprovado não sobe:

NívelPerguntaO que prova a passagem
N0 identidadeo que é, quem mantém, licença, está vivo?trajetória datada (commits, releases), não "é popular"
N1 capacidadeo que ela faz que o Onion não faz?os verbos da superfície executável (--help, API), nunca do marketing
N2 mecanismocomo faz, e onde mora o determinismocomportamento: rodou, ou leu o código-fonte
N3 transferibilidadeigual → transfere; diferente → desenhaa régua de transferência aplicada com evidência e refutador
N4 absorçãoo plano: artefato, costura, guarda, bancadanós x_absorb_* no grafo, que o /meta:forge lê

Toda dissecação que chega ao N3 fecha num de quatro vereditos, com razão escrita: absorver (o conceito entra no Onion, reescrito na gramática da casa), costurar (a ferramenta fica de fora e entra por adapter), parquear (técnica a investigar, com gatilho nomeado) ou rejeitar (com a razão datada, para ninguém reabrir). "Interessante" e "vale acompanhar" não são veredito. O comando não sela: ele grava o grafo da dissecação e deixa 1 nó decision aberto por ferramenta. Quem fecha é o /meta:decide, do bloco D.

A fronteira. Ferramenta de terceiro **roda em worktree ou container, nunca na árvore de trabalho**. É mecanismo, não disciplina: um refutador com instrução escrita para não escrever escreveu em seis arquivos (medido pela casa em 2026-09-20).

A ferramenta do exercício: yq (o processador de YAML de linha de comando escrito em Go; o repositório e a imagem oficial de container saem do próprio N0, da fonte primária). É plausível para este time: os grafos são YAML, e alguém sempre propõe "por que não lemos o .kg.yaml com yq em vez de awk?". É pública e roda num container.

Demo 1: o censo vem primeiro.

bash .claude/validation/dissect-census.sh . --markdown

Ele lista as dissecações que o corpus já pagou e o nível de cada uma. Ferramenta já dissecada com carimbo fresco entra no nível seguinte, sem repagar. Saída 3 quer dizer "não pude medir".

Demo 2: dissecar até o N3.

Peça 3 — .claude/validation/domain-anchor-census.sh

#!/usr/bin/env bash
# domain-anchor-census.sh — regra de domínio ancorada em DOCUMENTO é promessa; em CÓDIGO, é fato.
#
# Mede, nos nós rule/invariant/policy de um ou mais .kg.yaml, para onde o `trace:` aponta:
#   codigo    — caminho que casa DOMAIN_ANCHOR_CODE_RE (default: apps/ packages/ src/ lib/ services/)
#   documento — qualquer outro caminho (docs/…)
#   sem-trace — o nó não declara âncora
# Uso : domain-anchor-census.sh <grafo.kg.yaml>... [--strict] [--tsv]
# Exit: 0 medido · 1 (--strict) há regra ancorada só em documento ou sem âncora
#       2 uso inválido / arquivo ausente · 3 nada a medir (zero regras NÃO é resultado)
set -euo pipefail
export LC_ALL=C

strict=0; tsv=0; files=()
for a in "$@"; do
  case "$a" in
    --strict) strict=1 ;;
    --tsv)    tsv=1 ;;
    -*) echo "uso: domain-anchor-census.sh <grafo.kg.yaml>... [--strict] [--tsv]" >&2; exit 2 ;;
    *)  files+=("$a") ;;
  esac
done
[ "${#files[@]}" -gt 0 ] || { echo "uso: domain-anchor-census.sh <grafo.kg.yaml>... [--strict] [--tsv]" >&2; exit 2; }

CODE_RE="${DOMAIN_ANCHOR_CODE_RE:-^(apps|packages|src|lib|services)/}"
rows=""
for f in "${files[@]}"; do
  [ -f "$f" ] || { echo "arquivo ausente: $f" >&2; exit 2; }
  rows+="$(awk -v code_re="$CODE_RE" -v src="$f" '
    function flush() {
      if (id != "" && (nt == "rule" || nt == "invariant" || nt == "policy")) {
        k = (tr == "") ? "sem-trace" : ((tr ~ code_re) ? "codigo" : "documento")
        printf "%s\t%s\t%s\t%s\t%s\n", k, nt, id, tr, src
      }
      id = ""; nt = ""; tr = ""
    }
    /^  - id:/    { flush(); id = $3; next }
    /^  - from:/  { flush(); next }
    /^[a-z_]+:/   { flush(); next }
    id != "" && /^    node_type:/ { nt = $2 }
    id != "" && /^    trace:/     { tr = $2; gsub(/["\047]/, "", tr) }
    END { flush() }' "$f")"$'\n'
done
rows="$(printf '%s' "$rows" | grep -v '^$' || true)"

[ -n "$rows" ] || { echo "domain-anchor: nenhum nó rule/invariant/policy nos grafos dados — nada a medir. Recusa." >&2; exit 3; }

if [ "$tsv" -eq 1 ]; then printf '%s\n' "$rows"; else
  n_code=$(printf '%s\n' "$rows" | grep -c '^codigo'    || true)
  n_doc=$(printf '%s\n' "$rows"  | grep -c '^documento' || true)
  n_none=$(printf '%s\n' "$rows" | grep -c '^sem-trace' || true)
  echo "# âncora das regras de domínio · codigo=${n_code} · documento=${n_doc} · sem-trace=${n_none}"
  # `|| true`: sem nenhuma pendência o grep -v sai 1, e sob pipefail + set -e isso MATAVA o medidor
  # com rc=1 no caso bom (achado pela bancada no 1º ensaio).
  printf '%s\n' "$rows" | { grep -v '^codigo' || true; } | awk -F'\t' '{printf "  - [%s] %s `%s` → %s\n", $1, $2, $3, ($4 == "" ? "(sem trace)" : $4)}'
fi

if [ "$strict" -eq 1 ] && printf '%s\n' "$rows" | grep -qv '^codigo'; then exit 1; fi
exit 0

Peça 7 — .claude/validation/domain-anchor-selftest.sh

Com o /meta:forge, a bancada entra como a família run_domain_anchor_selftests no lint-selftest.sh; o script abaixo é o corpo dos casos, e a família pode simplesmente chamá-lo.

#!/usr/bin/env bash
# domain-anchor-selftest.sh — bancada do domain-anchor-census.sh.
# Todo caso tem de REPROVAR contra a versão defeituosa (o mutante). Caso que passa nos dois é decorativo.
# Uso: domain-anchor-selftest.sh [<medidor>]   (default: o medidor ao lado deste arquivo)
set -uo pipefail
export LC_ALL=C
M="${1:-$(dirname "$0")/domain-anchor-census.sh}"
[ -f "$M" ] || { echo "medidor ausente: $M" >&2; exit 2; }
T="$(mktemp -d)"; trap 'rm -rf "$T"' EXIT
pass=0; fail=0
check() {  # $1=nome  $2=rc esperado  $3=rc obtido
  if [ "$2" = "$3" ]; then pass=$((pass+1)); echo "  ✅ $1"; else fail=$((fail+1)); echo "  ❌ $1 (esperado rc=$2, veio rc=$3)"; fi
}
node() {  # $1=id $2=node_type $3=trace (vazio = sem trace)
  printf '  - id: %s\n    node_type: %s\n    status: open\n' "$1" "$2"
  [ -n "$3" ] && printf '    trace: %s\n' "$3"
  return 0
}
{ echo "nodes:"; node RU_A rule "apps/api/src/x.ts:10"; echo "edges:"; echo "  - from: RU_A"; } > "$T/code.kg.yaml"
{ echo "nodes:"; node RU_A rule "apps/api/src/x.ts:10"; node RU_B rule "docs/business-context/f.md:3"; } > "$T/doc.kg.yaml"
{ echo "nodes:"; node PO_A policy ""; } > "$T/none.kg.yaml"
{ echo "nodes:"; node EN_A entity "docs/x.md"; } > "$T/empty.kg.yaml"

bash "$M" "$T/code.kg.yaml" --strict >/dev/null 2>&1;  check "regra ancorada em código passa no --strict" 0 $?
bash "$M" "$T/doc.kg.yaml"  --strict >/dev/null 2>&1;  check "regra ancorada só em documento reprova no --strict" 1 $?
bash "$M" "$T/none.kg.yaml" --strict >/dev/null 2>&1;  check "política sem trace reprova no --strict" 1 $?
bash "$M" "$T/empty.kg.yaml"         >/dev/null 2>&1;  check "grafo sem regra recusa (exit 3, nunca zero silencioso)" 3 $?
bash "$M" --bogus                    >/dev/null 2>&1;  check "argumento desconhecido recusa (exit 2)" 2 $?
bash "$M" "$T/nao-existe.kg.yaml"    >/dev/null 2>&1;  check "arquivo ausente recusa (exit 2)" 2 $?
echo "# bancada domain-anchor: ${pass} ✅ · ${fail} ❌"
[ "$fail" -eq 0 ]

# Doutrina da âncora de domínio

Fragmento canônico. A skill `domain-anchor` referencia este arquivo; ninguém o copia.

## As três cláusulas

1. **Regra ancorada em documento é promessa.** Um nó `rule`, `invariant` ou `policy` cujo `trace:`
   aponta para `docs/` diz o que alguém escreveu que o sistema faz. Só a âncora no código diz o que
   ele faz. Enquanto a âncora for documento, a `confidence` fica abaixo de 1.
2. **A âncora se mede, não se lembra.** O estado entra na sessão pelo medidor
   (`.claude/validation/domain-anchor-census.sh`), e a linha do código sai de `grep -n`.
3. **Não achar o código é resultado.** Regra sem código vira pergunta aberta. Âncora inventada
   para o medidor passar é pior que âncora ausente, porque mente para quem volta ao porquê.

## O que esta doutrina NÃO promete

O medidor confere para ONDE a âncora aponta, não se o código faz o que a regra diz, nem se o
arquivo existe (isso é do `kg-trace-resolve.sh`). Ler o código e julgar continua sendo trabalho
de gente.
