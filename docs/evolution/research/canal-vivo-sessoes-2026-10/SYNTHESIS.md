# Canal vivo entre sessões — síntese (projeção do grafo)

> Projeção de `canal-vivo-sessoes-2026-10.kg.yaml`. O grafo é a fonte; este arquivo deriva dele.

## A pergunta
Como desenhar a classe 'live' da federation-transport (adapter por adotante: cc-peer|slack|teams|a2a) para comunicação DIRETA entre sessões Claude Code em máquinas e CONTAS diferentes, restrita a membros autorizados, com humano no circuito e o corpo da mensagem como DADO? Segue open: o Claude Code documenta transporte entre máquinas só dentro da MESMA conta; entre contas o doc é silente; Slack/Teams/A2A têm âncora de mecanismo, mas members.yaml não carrega identidade de plataforma.

## Restrições de desenho (claim aberta, NÃO decisão)
Restrições que a evidência ancorada impõe ao desenho da classe 'live' (NÃO é decisão): (1) cc-peer só vale DENTRO da mesma conta claude.ai por assinatura — serve ao maestro entre as próprias máquinas, não entre adotantes; vetado em org ZDR/HIPAA; corpo reside na Anthropic; portão humano de saída disponível via isolatePeerMachines=true no settings do projeto. (2) slack/teams não têm canal oficial sessão↔sessão: Channels é research preview, só interativo, com relay que transforma remetente em autoridade — nunca declarar relay entre orgs; Slack MCP exige app interno aprovado por admin; Work IQ fala COMO o usuário (delegado) e agentes no Teams só ouvem quando @mencionados. (3) a2a é a única via com âncora de identidade já no members.yaml (chave pinada), mas a spec deixa assinatura opcional e não trata conteúdo de agente como não confiável — o Onion precisa exigir as duas coisas. (4) toda via precisa de identidade de plataforma no members.yaml antes de qualquer allowlist.
